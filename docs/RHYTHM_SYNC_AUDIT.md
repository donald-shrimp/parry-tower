# 拍・到達・入力の同期監査（2026-10-22）

## 結論

v0.9.5-preview-4のコードは、ユーザーが求める「整数拍のビートと敵の振りの到達が一致する」を満たしていない。半拍についても同じ一定差がある。これを慣れだけの問題と扱わない。

音声出力時刻へ換算した譜面拍をB、敵の接触をC、入力中心をJ、個人補正をoとすると、現実装はC=B+100ms、J=B+o。100msは盾の立ち上げ時間を接触へ加算したもの（game.jsのsyncAttackClock/inputTargetAt）。入力補正で敵のモーションが動かなくなった点は維持すべきだが、固定100msを正しい設計とした以前の判断は見直す必要がある。

## 再現した挙動

実ゲームの既存VMハーネスを使い、通常/レア全26キャラ×新補正−100/0/+100×緩慢Lv0/6の156遭遇、各キャラの拍列を2周以上含む1,356攻撃を調査。全件でC−B=100ms（浮動小数点誤差のみ）。一時停止/再開でも同じ。整数拍/半拍、BPMに依存しないため、拍列の累積ドリフトとは異なる。

無強化・通常スキン・端末残差なしの模擬入力：

|保存の状態|読み込まれる新補正|拍で押す|到達で押す|
|---|---:|---|---|
|両キーなし|0ms|JUST|MISS|
|旧キー0msのみ|−100ms|MISS|MISS|
|旧キー100msのみ|0ms|JUST|MISS|
|新キー+100ms|+100ms|MISS|JUST|

通常の判定幅はJUST±11ms、PARRY±31ms。到達を見て押すと、無補正では100ms遅く判定される。旧0msが保存されていればJとCの隔たりは200ms。ユーザー端末の現在値/押し方は未確認であり、ユーザーの全ミスをこの模擬例だけで断定しない。

## 旧版からの移行

2a6ca59の直前コードではC=B+旧補正、J=C−100ms。旧キーがある場合は新補正=旧補正−100msなので、範囲内ではJを維持する。ただしCはB+100msへ動く。

旧キーがない場合、旧版は補正0ms相当でJ=B−100ms、新版は新補正0msでJ=B。キーを保存したことがない既存ユーザーでは、判定中心自体が100ms変わる。以前の「旧設定移行で体感を保持」の検証は、旧キーがあるケースと推奨値100msを中心にしており、この違いを十分に評価していなかった。範囲端のclampも別途扱う必要がある。

## 音楽・描画・既存検証

- BGM全8曲×通常/ボス×模擬出力遅延0/50/150msの48条件で、最初の対象拍に実際の音声ノード予約があり、出力換算後もC−B=100msを確認。初回の監査スクリプトは遅延150msで予約期限後へフレームを飛ばしていたため失敗。音声時刻の100ms前へ進める正しい予約条件で再検証した。
- 敵26キャラと騎士の実サンプラー座標テスト2件成功。指定接触時刻に剣先/攻撃点が盾へ一致することを複数画面幅/通常・パリィ・ガード等で検証。これは指定されたCへの幾何学的な一致であり、CとBの一致を保証しない。ユーザーの任意ポーズ調整後の見た目全体や全画素の当たりを保証する検証ではない。
- 時計/入力補正/境界/移行/測定等の関連34件成功。既存テスト自体がC=B+100msを正解としており、成功をユーザー要件の達成と同一視しない。
- 模擬出力時刻とノード予約の照合であり、実スマートフォンのスピーカー/Bluetooth出音、画面走査、タッチ遅延の実測ではない。成功SEは結果確定後に音声ノードを作るため、実際の出音との一致も今後の確認項目。

証跡：test-results/rhythm-audit/report.json（全行と入力例）、music-events.json、tests.txt、contact-geometry.txt。同フォルダのaudit.cjs/audio.cjsはテストハーネスの先頭部を利用した診断用スクリプトで、ゲーム配布物ではない。

## 次の修正の合格基準

1. 個人補正0/端末残差0の基準でB=C=Jをそろえる。個人補正はJだけを変え、BGMや敵の到達を動かさない。盾の100ms演出を敵の拍から切り離す。長押しガードの準備時間と成功パリィの見せ方は分けて検証する。
2. 初回/保存なしの既存ユーザー/旧キーあり/新キーありを区別して移行方針を決める。設定を勝手に初期化したり、現端末の値を未確認のまま決めつけない。
3. 全拍列と半拍・全テンポ・時空/緩慢・初撃/次撃/停止再開/第二楽章を同じ基準で検証する。補正の符号、境界の内外、遅い入力のフィードバックを確認する。
4. 30/60/120fpsとフレーム落ちで表示フレームの遅れを別計測。予定接触時刻の一致と実際に描かれた最初のフレームの誤差を分けて報告する。成功SEの予約/出力時刻も確認する。
5. Devで拍・到達・判定中心・入力誤差を同時に見られる確認手段を用意し、最後にユーザーの端末/出力経路で体感を確認する。

今回は監査とメモ更新のみ。ゲームの時計・判定・モーション・保存値・公開版は変更していない。
