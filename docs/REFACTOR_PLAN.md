# パリィの塔の段階的リファクタリング案

2026-11-06。調査基準は公開コミット `db87a1c` と同じ実装ツリー。ユーザー指定の GPT-6.1 Sol / high が実装し、親エージェントが設計・差分・独立比較をレビューする。最初の3PR相当はローカルの `refactor/audio-foundation` で実装・検証済み、未公開。実機の聴感確認と段階2以降はこれから。以下の構成・順序は実装時に段階ごとに評価する。

## 目的と完了の考え方

敵・スキル・曲・画面を追加するときに、変更先と確認すべき挙動を特定しやすくする。各段階で遊べる状態にし、個別のPRでレビュー・差し戻しができるようにする。

完成の目安は次のとおり。

- 曲を追加するときは曲定義と必要な音色を登録し、本編とDev試聴が同じ経路で再生する。
- スキルの数値を調整すると、戦闘計算と説明表示が共通の数値定義を参照する。
- ショップや図鑑を変更するときは、その画面と共有UIだけを読めば作業できる。
- 戦闘の計算をDOMやAudioContextの用意なしで確認できる。
- 保存する情報、ラン開始時に固定する情報、一時的な描画・音声情報の所有者が明確になる。
- 通常の機能テストは公開されたモジュールの入口を使い、ソース文字列への差し込み依存を段階的に解消する。

## 音声の整理方針

現在の音楽・SEはWeb Audioによる合成。最初の到達点は、ゲーム側から見た再生窓口を揃え、内部を次の責務に分けること。

| 責務 | 担当すること |
| --- | --- |
| 音声セッション | AudioContextの有効化・再作成、BGM/SEの接続と音量、ノードの終了処理 |
| 再生スケジュール | 拍の原点、先読み予約、停止・再開、予約済み接触音のキャンセル |
| 曲カタログと譜面 | 曲ID、選曲条件、拍ごとの音符・楽器イベント、Dev試聴用の情報 |
| 楽器と効果音 | オシレーター、ノイズ、金属音、開始の太鼓などの音生成 |
| 時計の対応付け | 既存 `audio-clock.js` を使った音声時刻と描画・入力時刻の対応 |

曲は曲ごとに分けたまま共通の登録・再生形式へ寄せる。最初は既存曲をアダプターで包み、音色パラメーターと譜面をそのまま移す。`game.js` 内の旧曲、追加アレンジ、カウントインも対象に含める。

時計の原点、音の生成、入力受付を同時に設計変更すると原因の特定が難しい。音源の移動と再生管理の移動は別PRにする。合成処理の共通化は波形・音量・アタックの差を確認した後に進める。

## 実施順序

20:02からの開始用に、以下の段階を [REFACTOR_EXECUTION](./REFACTOR_EXECUTION.md) で作業単位へ分割した。API・依存・検証・開始手順の正本は同書。2Aの [Sol開始指示](./SOL_REFACTOR_BRIEF.md) も用意済み。段階0〜1は完了、次はゴーサイン後に2Aへ着手する。

| 段階 | 主な作業 | 終了条件 |
| --- | --- | --- |
| 0 検証の土台 | テスト用ハーネスを専用ファイルへ移し、試算スクリプトから直接利用。重要な同期・保存・戦闘順序の既存テストを対応表にする | 現行テストが同じ挙動を検証し、試算がテスト本体の文字列抽出を必要としない |
| 1 音声 | 下記の小PRへ分割して音源と再生管理を抽出 | 曲追加と試聴が共通経路になり、BGM・接触・結果の時刻関係と音色を維持できる |
| 2 状態と保存 | `createRunState` 相当の初期化を抽出。恒久育成、ラン中の状態、入力、描画、音声の所有を整理。保存変換を専用境界へ集約 | 旧セーブ、購入後の新規ラン、中断再開、Devの保存抑制が一貫する |
| 3 戦闘と効果 | 数値計算から抽出し、その後で反撃・追撃・回復・撃破を順序付きの処理へ整理 | 既存の結果と適用順序が一致し、代表的なスキル追加が描画・保存・音声へ直接入り込まない |
| 4 画面と説明 | ショップ、図鑑、報酬、設定を画面単位に分離。数値と説明の参照元を揃え、共有部品のレイアウトを統一 | 現在値・次の値・上限が共通ルールで出て、スマホ幅でも揃う |
| 5 描画・Dev・配信 | 描画への入力を絞り、Devは共通の操作APIを使う。アート依存と生成物を記録。HTMLの依存一覧と版管理を一本化する | 本編・Dev・工房が同じ定義を利用し、配信参照を機械的に照合できる |

段階4の画面抽出は、状態の読み取り口ができた時点で部分的に先行できる。段階3の戦闘順序の整理は、音声と状態の境界が落ち着いてから行う。

### 最初に着手する範囲

1. **検証ハーネスの抽出**。対象は `tests/game-smoke.test.js` と `scripts/survival-analysis.js`。既存のコード差し込みはこの時点で一箇所に隔離し、ゲームの入口ができるごとに置き換える。全テストを一度に書き直す前提を作らない。
2. **楽曲・音色の抽出**。`scoreTone`、`scoreNoise`、`scoreFinalKick`、`playMusicStep` の責務を整理。最初の階層・通常曲・王の3曲と共通アレンジを含む。既存の予約処理を使って比較する。
3. **再生管理の抽出**。AudioContext、バス、先読み、停止・再開・予約キャンセルを共通窓口に寄せる。ゲーム側は曲とテンポ、時刻を渡す。Dev試聴と音量調整も同じ窓口を使う。

この3PR相当を最初の区切りにする。ここで実際の依存と変更量を見て、後続段階の分割を確定する。

## 境界を作るときのルール

- ゲーム進行の所有者は一つにし、UIと描画は必要な状態を読み取って操作を依頼する。新しい巨大な共有オブジェクトを各モジュールへ渡す設計は避ける。
- 数値計算は引数から結果を返す形に寄せる。乱数・時計・保存・音声は外部から渡せる入口にする。抽出の初期段階では乱数の消費順序も比較する。
- 追撃などの適用順序を明示し、撃破時の終了条件を保つ。表示用の通知を分ける場合も処理順序と即時性を明示する。
- 保存するランの情報と一時状態を分類してから保存項目を明示化する。項目の分類が済む前に保存形式を全面変更しない。
- 最初は現行のブラウザー公開APIとNode向けexportを利用する。ES Modules化はテスト・Dev・工房を含む小さな一経路で成立を確認して別段階で判断する。新しいフレームワークやバンドラーは、必要な効果と運用負担が分かった時点で選ぶ。
- ファイルを移すPRと、数値・仕様・音色を変えるPRを分ける。抽出した範囲は読める関数と変数名に整える。
- アートの削除は本編・初期モード・工房・試作ページからの参照を確認して対象ごとに判断する。生成物には生成元と再生成コマンドを残す。

## 各段階の確認

既存の全Node496件を起点とし、段階0〜1の最終候補は501件・画像8件・フォント2件が成功。追加は曲カタログ1件と音声寿命の境界4件。移す境界で既存テストが捉えられない挙動に絞る。音源の83条件・413,868操作、先読み予約の640条件が基準実装と一致し、耐久試算36比較とfixtureを含むJSONも一致。Chromeで本編/Devの開始・試聴・練習・一時停止/再開・Context再作成を確認した。

- **タイミング**。1.5拍前の予告、1.5拍以内の追撃、拍上の接触、入力補正、ヒヨコの判定幅、通常/精鋭テンポ、時計停止、再開、80F第二楽章。音声予約と判定結果を別々に照合する。
- **音色**。譜面イベントとノードの予約値を比較し、必要箇所を固定条件で書き出して試聴する。ブラウザー間では出力バイトの完全一致を条件にせず、アタック・音量・音色とタイミングを確認する。端末での聴こえ方と操作感はユーザーの試遊で確認する。
- **戦闘**。同じ初期状態・入力・乱数でHP、障壁、コンボ、奥義、追撃順序を比較。撃破を伴うケース、回復の切り上げ、余剰回復、上限超過障壁、復活を含める。
- **保存**。旧セーブの読込、購入済み強化、中断中のショップ購入、限界突破、遺物研磨、支払い済みイベント、保存失敗を既存ケースで確認する。
- **表示**。320px・390px・PC幅で、購入前後、MAX、長い説明の折返し、ゲージ幅とボタンの位置を確認する。
- **配信**。本編・Dev・工房の参照、静的チェック、生成アート、公開ファイルの一致を確認する。公開時は統合後のCIとPages完了まで確認する。

各PRで必要な既存テストと変更箇所の確認を行い、公開候補はリポジトリ規約の全チェックを通す。速度は同じ条件の直近計測と比べ、大幅に悪化した場合は原因を確認する。バランス試算は仮定を置いたモデルであり、実戦の結果確認には実際の戦闘コードのハーネスも使う。
